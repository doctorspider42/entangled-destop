# How the Venus executor serves every core Vulkan 1.0-1.3 command the
# protocol decodes. Read by `scripts/venus-exec-gen.py`, which refuses to run
# unless every such command is in exactly one section, and unless the two
# hand-written sections agree with the `match` arms that implement them.
#
# A line is one command; `#` starts a comment. Extension commands are not
# listed: no device extension is advertised, so every one of them stays
# refused as "decodable but not implemented".
#
# [bespoke]      Stages 5a.3 and 5b.1: hand-written end to end, host call
#                included (`VulkanContext::dispatch` in executor/context.rs,
#                `HostVulkan`'s typed methods). Also the list
#                scripts/venus-ash-gen.py builds its bridge for.
# [handwritten]  Stage 5b.2 commands whose executor logic is written by hand
#                (`VulkanContext::dispatch_objects`, executor/device_objects.rs
#                and executor/submit.rs): object bookkeeping, bounds against
#                objects the renderer knows, submission, waits. Every one of
#                them still uses the generated translation (ids to host
#                handles, enum and flag checks, counts) and the generated host
#                call.
# [generated]    Pure pass-through: the generated translation, the generated
#                host call, nothing else. No bookkeeping, nothing to bound.
# [refused]      Decodable core commands refused on purpose, fatal like any
#                unimplemented one. The comment says why.
