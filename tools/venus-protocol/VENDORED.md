# Vendored: venus-protocol generator at git-70991d4c (plus our Rust output)

- Upstream: https://gitlab.freedesktop.org/virgl/venus-protocol.git, commit
  `70991d4c7e4e5a7bfa2fbb8a6e77e4eac350145d` ("access pNext via real type to
  not violate strict aliasing", 2026-02-18). This is the revision Mesa
  26.2.3 bundles: its `src/virtio/venus-protocol/vn_protocol_driver.h` says
  `generated by venus-protocol git-70991d4c`.
- Verified: running the vendored `vn_protocol.py` (Mako 1.4.3, Python 3.12)
  with `--banner` built from `templates/banner.in` regenerates Mesa
  26.2.3's (commit `31e9a6b2`) bundled `src/virtio/venus-protocol/*.h` —
  all 38 driver headers — **byte for byte**. Mesa carries only the driver
  side; the renderer side comes out of the same model with `--renderer`.
- Licence: upstream has **no top-level LICENSE file**. Every source file is
  marked `SPDX-License-Identifier: MIT` (Copyright 2020 Google LLC); the two
  private registries in `xmls/VK_*.xml` are `Apache-2.0 OR MIT`; Khronos'
  `xmls/vk.xml` is `Apache-2.0 OR MIT` and the `include/` headers are
  `Apache-2.0`. All permissive; none of it is compiled into a shipped binary
  (the Rust it generates is ours, and the C headers exist only inside the
  differential harness).
- Not a Cargo crate and not a build dependency: nothing here runs during
  `cargo build`. It needs Python 3 and Mako at *regeneration* time only.

## What is verbatim

Copied from `git archive 70991d4c`, unmodified:

- `vn_protocol.py`, `vkxml.py` — the generator and its registry model;
- `xmls/` — `vk.xml` (VK_HEADER_VERSION 343) and the two private
  registries, `VK_EXT_command_serialization.xml` (the opcode table) and
  `VK_MESA_venus_protocol.xml`;
- `templates/*.h`, `templates/banner.in` — upstream's C templates;
- `include/` — the Vulkan headers matching that `vk.xml` (the harness
  compiles the C against them);
- `utils/`, `docs/`, `README`, `meson.build` — upstream's own helpers and
  build description, kept for reference (meson.build shows how upstream
  invokes the generator).

Upstream's `tests/` and `TODO` are not vendored.

## What we added

Nothing upstream is edited. Everything below imports `vn_protocol` and
`vkxml` as libraries:

- `rust_protocol.py` — translates `vn_protocol.Gen`'s model (in/out
  classification, partial encoding, validity, null-branch rules,
  `IGNORABLE_LIST`, chain lists, command grouping) into Rust over
  `crates/virtio-gpu/src/venus/wire.rs`. Refuses (`Unsupported`) any
  construct it does not translate yet: unions, strided arrays, nested
  dynamic arrays, blobs written straight into a reply, arithmetic `len`
  expressions, packed `uint16_t` arrays.
- `templates/rust_*.rs` — the Mako templates it renders (defines, info,
  group modules, dispatch).
- `rust-selection.txt` — which commands, which core API version and which
  extensions the generated chains admit.
- `harness/` — the differential check against the generated C (driver and
  renderer); see `harness/run_differential.py`.
- this file.

## Regenerating

```sh
python scripts/venus-gen.py          # with Mako installed; see its --help
```

CI job `venus-protocol` (`.github/workflows/ci.yml`) regenerates, fails on
`git diff --exit-code`, and runs the differential harness.

## Updating to a newer upstream revision

Replace the verbatim files from `git archive <rev>` of upstream, update
`VENUS_PROTOCOL_REVISION` in `rust_protocol.py` and this file, regenerate, and
run the harness. A renderer protocol newer than the guest's is harmless; one
older than the guest's is not (an unknown chain `sType` is fatal), so do not
go below the revision the supported guests' Mesa bundles.
